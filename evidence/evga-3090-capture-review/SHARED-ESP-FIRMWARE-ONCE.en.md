# Next test: boot the visible audit directly from firmware, without USB

[한국어](SHARED-ESP-FIRMWARE-ONCE.ko.md)

This test performs **no GPU transaction**. It selects the already-tested, already-installed visible audit directly through UEFI firmware for one boot, then the audit attempts its existing Windows handoff. The existing audit file is read and pinned to contributor SHA-256 `f4cf33771fcc1e9c463a94561898457d0ce6ee7e4e17da5546c8a9752d373c92`; it is not rebuilt/replaced. No ESP, Limine, Windows EFI, BCD, unlock log or transaction marker is written. The preparation writes only a new temporary `Boot####` variable and one-time `BootNext`, plus a new local recovery backup. **It never writes BootOrder.**

From the updated repository root in **administrator PowerShell**, run this one preparation command. The example uses your custom desktop drive; choose a new local directory outside the ESP if necessary:

```powershell
./research/profile/shared-esp-firmware-once.ps1 -StateDirectory 'G:\Movian\ESP-ONCE01'
```

Stop on an error; **do not reboot after an error or rollback refusal**. A successful JSON result must say `registered: true`, `boot_next_one_time: true`, `boot_order_written: false`, `limine_first_verified: true` and `windows_entry_verified: true`. Keep `G:\Movian\ESP-ONCE01\firmware-backup.json` outside the ESP, and keep recovery media available but unplugged for the test. The script does not restart the machine or close applications. Remove storage USBs, save work and **restart normally once**. Do not select an unlock EFI or change normal boot order.

Record video or photograph `AUDIT ENTERED ON PINNED ESP. Loading Windows in 10 seconds.` and report whether Windows login appears. There is no USB launcher message because no USB launcher is involved. Missing display is inconclusive; report it rather than retrying. This proves the new firmware launch path only if the audit entry is observed with USB absent; Windows boot alone is insufficient. It does not prove unlock or permanent automatic installation.

After Windows returns, remove the temporary selection/registration with one cleanup command:

```powershell
./research/profile/shared-esp-firmware-once.ps1 -Action Cleanup -StateDirectory 'G:\Movian\ESP-ONCE01'
```

The output should show `boot_order_unchanged: true`, `temporary_option_present: false` and `boot_next: null` (unless another tool has since created its own next-boot request). The local backup is retained. Restart once more to confirm ordinary Limine remains first and Windows/CachyOS entries work. Send prepare/cleanup output, audit photo/video and both boot results privately; keep the full backup private because it contains device paths. Do not delete the backup or use Prepare again with that directory.

To cancel **before** restarting, use the same Cleanup command. For read-only diagnosis use `-Action Status` with the same directory. If preparation fails after a write, it attempts to remove only its exact temporary variables, verifies readback and reports rollback failure explicitly. If no Windows within three minutes, power off and use the firmware boot menu's existing Limine or Windows entry. UEFI should already have consumed BootNext before entering the audit; the ordinary BootOrder was not rewritten. Recovery is not guaranteed. If needed, use recovery media to regain Windows, then run Cleanup. If existing state differs or cleanup refuses, preserve the backup/output and ask for review; do not guess/delete numbered firmware variables or blindly restore BootOrder.

**Risk and boundaries:** this test changes firmware NVRAM, which can be rejected, normalized or mishandled by firmware and can affect boot. Firmware execution may hang or reject an unsigned audit. Secure Boot must already be disabled; no security setting is changed. Backup/readback and conditional rollback reduce mistakes but cannot guarantee recovery or atomicity. Windows firmware APIs expose no compare-and-swap transaction: another firmware tool, update or firmware itself can race a read/write. Close other firmware/boot-management tools. The script refuses an existing BootNext, verifies the first active BootOrder entry is the pinned Limine path and a pinned Windows Boot Manager entry remains, snapshots all referenced entries and checks their bytes/attributes repeatedly. An unexpected existing-state change stops the operation; it does **not** overwrite that change with the backup. Cleanup rechecks exact owned BootNext/option bytes and attributes immediately before deletion and preserves a foreign next-boot request.

**Actual mechanism:** this is direct UEFI NVRAM through Microsoft's `GetFirmwareEnvironmentVariableExW`/`SetFirmwareEnvironmentVariableExW`, temporarily enabling then restoring `SeSystemEnvironmentPrivilege`. It does not use Windows BCD `/bootsequence`. The new option uses an active `EFI_LOAD_OPTION` with a GPT hard-drive short-form device path and the exact audit file path. The option and BootNext variable attributes are NV|BS|RT (`7`); the load option's separate active attribute is `1`. BootNext is one little-endian UINT16 identifying that option; UEFI specifies consumption before transferring control, then ordinary BootOrder. See [UEFI boot manager semantics](https://uefi.org/specs/UEFI/2.11/03_Boot_Manager.html), [Microsoft variable reads](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getfirmwareenvironmentvariableexw) and [writes/deletion](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-setfirmwareenvironmentvariableexw).

Local validation on 2026-10-28: 18 RAM-only binary/state-machine checks passed, including pre-existing BootNext refusal, immutable-backup failure, BootNext write failure, exact rollback, foreign BootNext preservation, BootOrder-change refusal, changed option/attributes and deletion races. An independent Python decoder verified the generated UEFI packed layout, GPT signature/geometry, file path and end node. Native bridge compiled; a separate RAM-native fixture ran the real entry script through local-path validation, WhatIf, Prepare/backup, Status, preboot cancellation, postboot cleanup and hash/BootNext/SecureBoot/Limine-order refusal. Script syntax checked. **No native firmware API was invoked and no actual NVRAM/ESP/hardware was accessed by these tests.** This firmware-selection route remains hardware-unverified. Firmware policy, Windows access restrictions, unavailable privilege, unexpected boot-option layout or hash changes can cause a refusal; send the exact error rather than bypassing it.
