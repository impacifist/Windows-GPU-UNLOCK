# Gigabyte B550 AORUS ELITE AX V2 / RTX 3090 headless USB evidence (local profile, no iGPU, EDID driver bound)

## Provenance and build scope

Contributor-reported result from one machine on 2026-10-27, made with a local profile generated by
`research/profile/make-profile.py` from two read-only probe captures of that machine. It is not a
reviewed machine profile and not a maintainer-operated hardware test. The EFI hashes in
[summary.json](summary.json) depend on that machine's `profile-local.h`.

**Build base, stated plainly:** the probe, the generator and the unlock were built from a local branch
of `5c98f11` (before #49 landed). That branch carried its own equivalent of #49's changes:
- a probe bus pin, the same idea as `build-probe.ps1 -TargetBus`;
- a profile bus constant, the same idea as `GU_TARGET_BUS`;
- acceptance of no iGPU;
- a local `proven.json` entry for nvgop `0x60009`.

Current `main` refuses these captures ("no PciIo attribute record"). They predate that probe change, so a
re-capture with the current probe is needed before this machine can go through today's pipeline. That run
has not been done yet.

## Machine

Gigabyte B550 AORUS ELITE AX V2 (BIOS FF, AMI), Ryzen 7 5800X (no iGPU), NVIDIA-subsystem RTX 3090
24 GiB (GA102, `10de:2204` / `10de:147d`, VBIOS 94.02.4b.00.0b) at `0000:07:00.0` behind root port
`00:03.1`. No other display adapter.

| | B550M evidence (`b550m-3090-usb`) | This machine |
|---|---|---|
| Board vendor | MSI | Gigabyte |
| RTX subsystem | `1462:3881` (MSI) | `10de:147d` (NVIDIA) |
| RTX PCI bus | `0x2b` | `0x07` |
| AMI EDID/mouse driver on the RTX GOP | none bound (`GU_NO_EDID_DRIVER`) | **bound**; stage 3 ran and detached EDID on two display children |
| nvgop | `0x60009`, `.text` `d045cee2...` | same build: `0x60009`, `.text` `d045cee2...`, Stop RVA `0x698` |

So this run covers the no-iGPU route **with** the EDID stage, which the B550M run skipped.

## CSM must be off (what a CSM-on capture looks like)

The first probe captures were taken with the BIOS default **CSM Support = Enabled**. In that state:
- AMI **CsmVideo** (`29CF55F8-B675-4F5D-8F2F-B87A3ECFD063`, EDK BiosVideo) owned the RTX PciIo instead of `nvgop-ga1xx`;
- the PCI command register was `0x0007` (bus mastering **on**), so the probe refused the deep read with `probe-unreviewed-envelope`.

With CSM disabled, the command register read `0x0003`, nvgop owned the card, and both captures were complete.
That matches the B660-PLUS note that CSM moves card ownership. A CSM-on capture is not a hardware fault, so
it seems worth checking for in the generator's refusal text.

## Recorded hardware run

Route: headless wrapper/child from a FAT32 USB stick (`GU_USB_MEDIA`), chosen in the firmware boot menu
after a full shutdown.

| Run | Boot | Entry SS0 / SS1 | Result |
|---|---|---|---|
| AUTO000000 / HLS000000 | cold boot after a full shutdown | `0x55464163` / `0x5` | `FINAL status=0 clean=1`, one FLR, Windows started directly |

After FLR: `SS0=88888888 SS1=00000008`, BME=0, no pending or retained mappings. The wrapper log shows:
1. console preparation;
2. EDID detach on both RTX display children;
3. NVIDIA GOP detach and the IO/MEM decode restore;
4. `verify-complete` and Windows `StartImage`, all with status 0.

See [report-excerpt.txt](report-excerpt.txt). One run only: repeated cold boots and Windows restarts were not tested.

## Measurements

PyTorch 2.13.0+cu130, `torch.matmul`, FP16/BF16 with FP32 accumulation (reduced-precision reduction
off), TF32 on/off as labelled. Each figure is the median of three runs of 30-sample medians after a 2 s
warmup. Windows 11 Pro 26300, NVIDIA driver 616.92, 350 W power limit (stock), same script before and
after. The locked baseline was taken in the same Windows session before the unlock boot.

| TFLOPS | n=4096 locked | n=4096 unlocked | n=8192 locked | n=8192 unlocked |
|---|---:|---:|---:|---:|
| FP32 (control) | 23.5 | 23.5 | 24.2 | 24.3 |
| TF32 | 34.0 | 56.3 | 36.8 | 61.6 |
| FP16 (FP32 acc) | 66.7 | 112.0 | 68.5 | 110.9 |
| BF16 (FP32 acc) | 67.7 | 114.2 | 70.0 | 113.9 |

These numbers do not cover application speed, long-term stability, sleep/hibernate or repeated boots.
