# 이슈54 검증과 AD104 절차 검토

[English](ISSUE54-VALIDATION.en.md) | [한국어](ISSUE54-VALIDATION.ko.md)

2026-10-27 [이슈54와 토론](https://github.com/impacifist/Windows-GPU-UNLOCK/issues/54), [공유 소스 리비전09ab194a9d9446c2bd56318815e459984a46d5ad](https://gist.github.com/yakold/31c18ec34eea889dce4222c59b7a2cdf/09ab194a9d9446c2bd56318815e459984a46d5ad), 자체 소스와 비공개 실제 캡처4세트를 검토했다. 외부 코드나 하드웨어 시험은 실행하지 않았다. 소스 파일 해시와 비공개 정보를 제외한 요약은 [검증 증거](issue54-validation-evidence.json)에 있다. 누락된 파일이나 이전/이후 어느 빌드가 작성자의 실제 결과를 만들었는지는 인증할 수 없다.

## 소스로 확인한 수정 사항

| 주장 | 증거와 수정 |
| --- | --- |
| 공유 할당기는4GiB 아래 페이지와 PCI DMA 매핑을 사용한다 | 고정한 gist의 linux_env.c199~220은 AllocateAnyPages/EfiBootServicesData를 사용하고 물리 할당 주소를 DMA 주소로 반환한다. 장치를 무시하며 Map 호출이 없다. 포인터 캐스트를 원래 주소와 비교해도 장치 주소 변환은 검증되지 않는다. 매핑 버전은 다른 리비전일 수 있지만 제공된 소스는 이를 입증하지 않는다. |
| 공유 실패 경로는 Falcon 중지 후 FLR을 수행한다 | unlock_uefi.c591~597에는 트랜잭션, 엔진 덤프, 공유 자원 해제, 반환이 있다. 설명한 실패 전용 halt/FLR 분기는 없다. upstream 트랜잭션 코드는 누락되어 어디에서도 정리하지 않았다는 증명은 아니다. 복구5회 성공은 작성자 보고로 남는다. |
| EFI_FILE_INFO.FileSize 오프셋은16이다 | 표준 FileSize는8, PhysicalSize는16이다. linux_env.c708 주석은 틀리지만712/721은 타입 구조체와 필드를 사용한다. 실제 포함 헤더 없이 기능상 오프셋 버그라고 할 수 없다. 자체 handoff도 타입 필드를 사용하며 호스트 ABI assertion으로 두 오프셋을 확인하도록 했다. |
| 백만 회500ns 읽기가9분을 설명한다 | 1,048,576×500ns=0.524288초다.9분/0.567초는 약952배이고1바이트→8바이트만으로는 트랜잭션 수가8배 줄어든다. 측정/대기/플랫폼 정보가 필요하며 제시한 산술은 해당 시간의 설명이 아니다. |
| 이 산출물은 DXE 드라이버다 | build-c.sh24는 efi_application을 지정한다. OS 전 실행되는 EFI 애플리케이션이며 실행 환경만으로 PE 하위 시스템이 EFI 드라이버가 되지 않는다. |
| DMA 모드는 할당과 재읽기를 검증한다 | unlock_uefi.c386~410은 각 버퍼를 순서대로 할당/접촉/해제한다. 명시적인 바이트 재읽기 비교가 없다. 자체 계획에서 추가로 고려할 한계는 트랜잭션 전체 동시 할당이나 장치 DMA 정확성의 증거가 아니라는 점이다. |
| c1 모드는 카드를 건드리지 않는다 | unlock_uefi.c426~434는 PCI command/BME를 바꾸고 복원한다. 읽기 전용 열거가 아닌 PCI 설정 쓰기다. |
| 체크포인트 로그 신뢰성 | uefi_lib.c242~277은 LocateProtocol로 SFS를 고르고 이전 로그를 삭제한 뒤 교체한다. 짧은 쓰기와 Close 결과를 확인하지 않으며 ul_mark는 반환값을 버린다. 로드 이미지 볼륨을 명시 선택하지 않는다. 저장 의도는 있지만 이 경로로 검증되지는 않는다. Close는 flush할 수 있으며 문제는 볼륨 선택과 오류 처리다. |

[UEFI 미디어 규격](https://uefi.org/specs/UEFI/2.10/13_Protocols_Media_Access.html#efi-file-info)은 파일 구조체를 정의한다. [PCI I/O Map](https://uefi.org/specs/UEFI/2.10/14_Protocols_PCI_Bus_Support.html)은 장치에서 보이는 주소를 제공한다. 이식 가능한 DMA 계층에서 CPU 물리 주소와 장치 주소를 동일하다고 가정할 수 없다. Map이 있다는 것만으로 동작/매핑 바이트 수/수명/동기화가 입증되는 것도 아니다.

## 더 좁게 해석해야 하는 주장

- 레지스터 목록은 실제260개(64+16+8+128+32+12)다. 같은 샘플이 전체 내부 상태 일치나 바인딩의 인과 효과를 증명하지 않는다. 단계, 바인딩, 리셋/전원 이력, 목록 해시, 읽기 폭, 시간 표시가 필요하다. 다른 부팅 간 비교도 표시를 명확히 하면 유용하지만 동일 전원 주기 동등성은 아니다.
- BADF5620은 여기서 유효하지 않은 관측 데이터다. 이것만으로 펌웨어 시작/충돌을 증명하지 않는다. 자체25/28/30은 업로드한 펌웨어를 실행하지 않고도 이 패턴을 다른 주소에서 반환했다. 상관관계는 공통 원인 진단이 아니다.
- [UEFI 부트 관리자 규격](https://uefi.org/specs/UEFI/2.10/03_Boot_Manager.html#load-option-processing)은 해당 부트 항목으로 제어를 넘기기 전에 BootNext를 소비하도록 요구한다. 소비 전 전원 손실에서는 비휘발성 값이 남을 수 있지만 애플리케이션 내부 정지 후 반복 실행은 보편 규칙이 아니다. 실제 변수 상태/펌웨어 동작을 기록해야 한다. 자체 수동 USB 경로는 BootNext/BootOrder를 쓰지 않는다.
- 제공된 증거는1GiB ESP나 특정 부팅 우선순위를 GPU 잠금 해제 필수 조건으로 입증하지 않는다. 부팅 선택과 실제 GPU 상태를 구분한다.
- halt/FLR 정리도 장치 상태를 바꾸거나 실패할 수 있다. AD104에서 미검증이며 이번 검토로 추가하지 않는다. 캡처/디코딩 해제 복구는 실행/실패한 FWSEC 트랜잭션 복구가 아니다.

## 자체 증거와 수정

기존 이슈 답글은 각 작성 시점의 자식 제거와 부모 해제를 올바르게 구분했다. 이후 [13~18차](AD104-THIRTEENTH-EIGHTEENTH-RESULT.ko.md)는5단계 그래프8→6→5→4→3→2, 대상 PCI BY_DRIVER 소유 관계 제거, command7→0/attributes718→0을 입증했다. 이는 새로 관측한 대상 관계 변화이며 재사용되는 전역 DriverBinding 이미지 언로드나 모든 펌웨어 활동 부재의 증거가 아니다. FWSEC 트랜잭션은 뒤따르지 않았으므로 해제가 보고된 AD103 실패를 해결하는지는 미검증이다.

[29차](AD104-TWENTY-NINTH-RESULT.ko.md)는 실패한 관측을 보존하며 별도로 제한 복구를 기록했고 사용자가 Windows 자동 진입을 확인했다. [30차](AD104-THIRTIETH-RESULT.ko.md)는 BCR 반환 거부 후 Windows 이전 명시적 중지를 기록하며 사용자의 복구 기억은 불확실하다.25/28/29/30 각각36개 파일을 저장된 원장 해시와 다시 비교했다.58%는 동일 가중치 이정표15/26을 반올림한 정확한 체크리스트 수치이며 확률/시간/해제 비율이 아니다. 수치를 올릴 근거는 없다.

[31차](AD104-THIRTY-FIRST-BOOT.ko.md)는 아직 실행하지 않았다. 산술 자체는 오프라인으로 이미 검증되었고 부팅은 통합/복구 증거만 추가한다. 거부된 세 주소를 제외하고 하드웨어 승인 범위나 펌웨어 진입 자격을 바꾸지 않는다. 이번 검토로 스테이징 EFI/소스 고정값은 바뀌지 않는다. 이전13~18차 영문 보고서의 이중 인코딩된 화살표/한국어 링크는 정확한 가역 변환 검사 후 복구했으며 사실은 그대로다.

## 적용한 절차

1. 다른 보고서의 제외 가설을 받아들이기 전에 소스 리비전, 실제 EFI 해시, ABI 헤더, payload 해시와 빌드 인수를 고정한다. 설명과 소스가 다르면 실제 결과에 대응한 버전을 요청한다.
2. 반환 상태/데이터 유효성, 소유 관계/설정, 디코딩, 복구 분기, 사용자 결과를 각각 기록한다. StartImage-next에서 Windows 시작을, 누락 로그에서 멈춤을 추론하지 않는다.
3. 기존 로드 이미지 볼륨 선택, 캡처 덮어쓰기 방지, 파일 함수 고정, 바이트 수/flush/재읽기/해시 검증을 유지한다. 이는 증거 신뢰성 개선이지 장치 실행 안전성 증명이 아니다. 광범위한260개 읽기, 넓은 MMIO 최적화, 리셋, 모드 파일 실행은 구체 범위의 별도 검토 없이 채택하지 않는다.
4. 보존 후 새 읽기 전용 요약기를 로컬에서 사용한다.

```powershell
python -I research/profile/attended-result.py "<saved capture>/DIAG00.TXT" --status "<saved capture>/STATUS.TXT" --operator-return unknown
```

automatic/manual은 사용자가 확인한 경우만 선택하고 기본은 unknown이다. 모순된 증거는 inconsistent로 표시하며 복구 성공 후에도 거부 관측을 유지한다. 잠금 해제 권한을 부여하거나 자료 출처/전체 로그 검토를 대체하지 않는다. 제한된 크기의 로그만 읽고 비공개 정보를 제외한 JSON을 출력하며 USB/하드웨어는 변경하지 않는다.

실행 시험 전 실제 매핑/정리 전체 구현, 단계가 맞는 원시 로그와 정확한 자산을 확보하고 동시 할당, 매핑 크기/수명/동기화와 실패 복구를 먼저 오프라인 검증한다. 현재31차는 그대로이며 이번 검증 결과를 얻기 위해 새 부팅은 필요 없다.
